# Auditoría estática de seguridad

Tres funciones nuevas en private, seis argumentos tipados con defaults originales. Todas STABLE SECURITY INVOKER, search_path explícito pg_catalog/public/private (base wrapper pg_catalog/private). Ninguna SECURITY DEFINER, DML, tabla, índice, job, cache persistente o modificación de políticas. PUBLIC/anon/service_role no reciben execute; authenticated tiene execute solamente en las tres nuevas funciones. No se modifican grants de funciones/vistas originales.

Core y entry de serie derivan usuario/rol/negocio de profiles por auth.uid, no de p_cursor ni del JSON interno. Cursor original valida asOf/requestKey/revision/offset, sin autoridad sobre negocio. El wrapper de base invoca core autorizado. Super_admin no se normaliza a owner. La condición NULL explícita se documenta para revisión: el baseline tiene role NOT NULL y enum check, pero si el destino no conserva esas constraints no puede afirmarse equivalencia con original NOT IN.

La vista original security_invoker/security_barrier no se modifica. **El candidato usa sus tablas y su tipo compuesto; no ejecuta su barrera de vista al preparar eligible.** Esto es una diferencia de arquitectura que debe revisarse: RLS de completions/orders/finanzas y comprobación statistics_can_read siguen activas, el principal está fijado en servidor y eligible MATERIALIZED separa filtros de autorización/fechas de la evaluación de composición. No presentar esto como conservación textual del security_barrier. Ningún predicado arbitrario de usuario puede inyectarse en la consulta privada; las llamadas siguen bajo invoker y la función source_items conserva su propia autorización. Debe auditarse seguridad del plan y llamadas directas en F.2B.

Bundle devuelve columnas que un authenticated autorizado ya puede seleccionar en effective_facts; siempre de su negocio y cohort permitido. No devuelve current_digest nuevo como columna adicional ni acepta un bundle suministrado externamente. La interfaz pública candidata proyecta legacy+series, no effectiveFacts. ACL de private y helpers debe verificarse de forma efectiva: no basta comprobar textos grant.

No se comparte materialización entre conexiones/usuarios. Memoria PLpgSQL request-local; sin tablas temp, settings que modifiquen rol, JWT, auth, cache o policies dentro de funciones. No lock de escritura ni FOR UPDATE agregado. RLS es además defensa independiente frente a cambio de perfil o RLS error; el candidato no elimina comprobaciones repetidas por policy para obtener rendimiento.

Pendiente: PLpgSQL compilation, catálogo de invoker/volatility/ACL, RLS multi-tenant real, búsqueda de funciones shadow, error/leak timing, roles/NULL (si representable sin alterar schema), falta de perfil, settings timezone/DST y concurrencia. No se contactó ninguna base en F.2A y la auditoría lexical no sustituye esos checks.
